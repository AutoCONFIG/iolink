## 阻断项及最小修订要求

### B01：完成状态缺少可信验收基线

证据：`PLAN.md:25–40` 的 M1 全链路通过、M2 待完成，与 `IMPLEMENTED.md:18–86` 的各模块全部完成、`FRONTEND-HANDOVER.md:80–83` 的待补字段相互冲突。后者又把“代码存在”“已提交”“架构保证”作为完成依据。

影响：无法确定本轮是补实现、修缺陷，还是仅补验收，工期和依赖判断均失真。

修订：建立稳定需求 ID，每项记录需求来源、实现位置、验收用例、执行环境、证据、结果和阻塞项。统一为“未实现／部分实现／实现待验收／验收通过／外部阻塞”。无本次可复现证据的历史勾选保留为历史声明，不继承为已验收。

### B02：管理端与微信用户之间缺少归属闭环

证据：`PLAN-DETAILS.md:61–84`、`FRONTEND-HANDOVER.md:87–91` 的流程没有分配或认领步骤；`internal/adminapi/handlers.go:16–36` 创建农场固定以管理员 aid 为 owner；`internal/core/users.go:27–37` 微信首登新建用户；`internal/core/repos.go:18–22` 按 owner 过滤池塘；`internal/core/notify.go:45–50` 也沿 owner 查通知接收人。

影响：正常操作创建的微信用户没有后台创建农场的所有权，无法形成“后台配置→小程序看到数据→本人收到报警”的交付闭环。

修订：明确用户邀请/认领/管理员分配中的一种基础流程，定义鉴权、归属变更、解除关联和通知接收人规则；补 API、页面及真实数据库验收。M6 再扩展组织与成员权限，但基础用户归属必须在 M3/M4 前完成。

### B03：数据隔离被当作架构结论，没有验收门槛

证据：`IMPLEMENTED.md:50–57` 声称全部查询受 owner 约束；`internal/appapi/handlers.go:79–86,112–176,193–208` 的池塘详情、设备详情、最新值、历史值及确认报警路径未检查 uid 对资源的所有权，相关仓储按裸资源 ID 查询/更新。

影响：列表过滤不能证明详情和写操作隔离。现有 M1/M4 验收即使走通单用户成功路径，也会漏掉此问题。

修订：把双用户互访/确认他人报警的拒绝用例加入基础交付门槛；M6 增加跨租户、跨角色、API-Key 范围及异步任务的同类验收。不得以新增多租户代替修复现有用户边界。

### B04：契约尚不足以冻结并行开发

证据：`docs/api/admin-openapi.yaml:10` 顶层 tags 结构与 app 契约不同；多个成功响应缺 description、响应 schema；`mqtt-spec.md:3,36–45` 仍是草案且不含 signal；`PLAN-DETAILS.md:66` 约定历史曲线含 unit 且不超过 200 点，`internal/appapi/handlers.go:167–176` 不返回 unit，`internal/core/repos.go:117–147` 未使用 maxPoints；前端交接还引用不存在的 `GET /api` 数据接口。

影响：仅有路径清单不能保证前端 mock、实现和实际响应一致；“先冻结契约即可全并行”没有成立条件。

修订：逐端点定义请求/响应、错误、分页筛选、时间及空值语义；明确字段和单位、signal、设备详情/绑定边界；采用 OpenAPI 校验和响应契约测试。M6 动态物模型必须定义对水质 v1 的兼容策略。

### B05：新安装与升级路径没有可执行基线

证据：`schema.sql:86–95` 缺 signal，但 `internal/core/pipeline.go:26–34` INSERT 包含该列；`DEPLOY.md:70` 称启动自动幂等迁移，实际 Compose 仅挂载数据库初始化脚本，应用没有相应迁移流程。

影响：干净环境的遥测写入会失败；重建应用镜像不能完成旧库升级。以现有 M1/M5 勾选直接开始扩展会掩盖基础阻塞。

修订：把可版本化迁移、空库初始化、现有库升级和失败恢复放在基础修复阶段；新增“仅依靠仓库文件从零安装后完整上报”的集成验收，禁止以手工改过的旧环境替代。

### B06：生产化验收缺少恢复、失败处理和可复现检查

证据：`DEPLOY.md:49–57` 仅给业务备份恢复示例；`deploy/backup.sh:10–13` 固定容器名并分别 dump 业务/时序，未提供恢复演练证据；`CONTRIBUTING.md:29–32` 要求每包测试和 make verify，但 core 没有测试，Makefile 保留已删除 contracts 路径。

影响：存在备份文件不等于可恢复；基础校验命令本身不能通过，无法作为各阶段退出门槛。

修订：定义完整备份/恢复演练（含 Timescale 时序数据和扩展）、数据核对、升级回退、服务探活、重启在线状态；修复验证入口并补核心数据/报警集成测试。明确恢复目标及测试环境，性能数字必须来自实际测量。

### B07：M6–M8 仍是功能名清单，缺少实施依赖和逐项验收

证据：`PLAN.md:88–123` 的 M6 同时装入 License、产品模型、开放 API、离线交付、租户与 RBAC，却仅有三条宽泛验收；M7 仅“地图看到／大屏刷新／视频点开”；M8 仅“对应功能位、状态同步”。`PLAN-DETAILS.md:202–210` 验收表停在 M5。

影响：即使全部功能名各有一个入口，也无法判定实现满足要求；定时/联动/调试依赖的命令生命周期未先定义，视频和网关也没有交付边界。

修订：保持 M0–M8 全量范围，拆为可验收子阶段；补数据模型→身份和权限→接口→任务和外部集成→双端 UI 的依赖图。每个子阶段明确进入条件、产物、成功/失败/重启/越权用例及证据。

### B08：扩展能力的关键产品语义未确定

证据：`PLAN.md:94–121` 只列技术名称；缺少 License 过期时既有采集/历史访问的行为，多产品版本迁移、密钥撤销与重放、任务幂等重试、命令过期/回执、网关子设备归属、报表任务、视频访问范围等定义。

影响：这些选择直接决定数据模型和用户可见行为，若边写边猜，后续阶段会推翻前序实现。

修订：建立各阶段设计附件，先定必要语义，再冻结相应契约；License 签发私钥与运行时校验分离；动态字段兼容存量数据；开放接口定义签名、作用域及限流；下行能力先有命令生命周期，再做调试台、定时和联动。

### B09：范围与架构表述互相冲突

证据：`PLAN-DETAILS.md:3` 限制“原需求没有的不进范围”，而 `FEATURE-MATRIX.md:75–88` 要求补全商业能力；`PLAN.md:18,134` 将多租户、复杂协议及远控列为重评触发，却已将它们列进 M6/M8；`PLAN.md:13,107` 同时承诺单程序交付与引入流媒体网关。TCP 在功能清单中又同时被列为缺口和“不计划”。

影响：扩展到底属于已定范围还是需要重新选型无法判断，“单文件整平台”与视频部署成本也会误导交付。

修订：以本次用户确认的 M0–M8 为新增需求来源，区分核心 iolinkd 单程序和数据库/反代/流媒体等配套服务。明确裸 TCP、OTA、驱动市场等是否在既定 M0–M8 范围外，不能由“不做”图例和欠账统计互相覆盖。

还需纠正 `docs/README.md:3` 的“冲突以代码为准”：经审定需求决定验收标准，版本化契约约束接口，实现偏离它们时进入缺陷清单；不能因代码当前如此就自动降低需求。

### B10：外部条件被写成“无阻塞”

证据：`IMPLEMENTED.md:89–98`、`PLAN.md:51–64,106–123` 依赖微信真机、固件、DTU/摄像机等，但没有可执行的输入清单、准备时间及替代验证边界。

影响：模拟器通过只能证明软件侧，不能证明真实微信发送、真实采集、视频兼容或控制命令已交付。

修订：每阶段列出凭据、模板、域名证书、硬件型号、寄存器表、视频协议版本和测试设备等所需输入；能用 fake/simulator 验证的先完成，真机部分保留独立“待外部验收”，不得整体勾完成。

## 其他应同步清理的问题

- 后台页面出现 6、6+1、6+2 多种口径；改为明确页面 ID 和对应接口，不用总数代替范围。
- PLAN M6–M8 插在“分工”章节中，主里程碑与责任分工应分开组织。
- 500 台每分钟一条约为 72 万条/日；约 14.4 万对应 100 台。容量目标、保留期、磁盘预算、查询延迟应基于同一规模。
- 商业矩阵中的“私有化部署 100% 就绪”“唯一技术缺口”与前端、迁移和联调待办不符，应删除未经验收的交付结论。
- 报警级别需统一按上下限自动判断还是由规则 level 决定；设备绑定/解绑/调塘及删除后历史保留必须定义；这些差异不能交由前端猜测。
- 部署中的 MQTT TLS 示例需补完整配置和证书位置，并明确原始端口绑定；REPORT_INTERVAL/OFFLINE_GRACE 文档称可配但主程序写死，纳入实现审核。
- 历史资料缺失、跨仓用语、旧基座描述和文档更新时间需统一；参考项目功能和报价不作为当前实现证据。
