## Authorization / farm access seams

- Do not trust caller `tenant_id` or `farm_id`: design says camera→pond→farm→tenant and derive the farm/tenant from the selected pond (`docs/design/M7a-video.md:9-14,28-33`). `internal/core/admin_store.go:88-155` shows existing service transaction pattern: tenant from request context, authorize in transaction, verify ownership/active tenant membership, insert and commit. Farm owner reassignment: `:302-386` locks the farm `FOR UPDATE`, scopes by tenant, validates the new owner belongs to tenant, writes farm + farm_membership + audit atomically. Farm reads use tenant filter (`:68-85`).
- Mini's live farm visibility predicate is `internal/core/app_resource_scope.go:10-32`: active tenant, user membership, owner or active farm membership; support is constrained to expiring support membership. Reuse/extract this semantics for camera list/detail/playback instead of authorizing by tenant alone. `appFarmConfirmScope` `:34-49` also binds current role and permission version.
- Transactional authorization exemplar: `internal/core/telemetry_authorization.go:14-57` validates actor/tenant/claimed role/version and uses `FOR SHARE OF tm,t,u` while checking active rows before write. Tenant member changes increment member and tenant permission versions in `internal/core/tenant_members.go:60-97`. Design prescribes shared locks in stable order `tenant→user→membership→farm→camera→session` for playback/source change/revocation (`docs/design/M7a-video.md:62-68`); farm owner/assignment/deletion and membership mutation paths must invalidate or live-check sessions, not just rely on JWT.
- Farm owner and membership edits already have tenant-scoped tx/audit mechanics; however M7a race-safe cross-operation lock order has not been implemented. Explicit risk: a management handler checking only token tenant/role can disclose another farm's camera or allow member/viewer config writes.

Keep License denial distinguishable from provider disabled per contract/design.
