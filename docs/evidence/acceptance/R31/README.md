# R31 software evidence

Using container `iolink-todo9-pg` (TimescaleDB image pinned by digest), `deploy/backup.sh` produced a custom-format full-database dump, a portable SHA-256 sidecar containing the dump basename, and metadata containing PostgreSQL/Timescale versions and the migration row count. With `IOLINK_RESTORE_TARGET=isolated` and a database named `iolink_restore_*`, `deploy/restore.sh` restored it into an isolated database only when the target PostgreSQL and Timescale versions matched; a non-empty incompatible target migration count is rejected before `pg_restore`, while an empty target is allowed. It then compared the restored migration version, farms/ponds/devices/sensor_data/device_shadows/alarms counts and min/max timestamps, public index count, and the Timescale retention-job count against the backup metadata and summary. A tampered archive failed checksum validation before restore, and a non-isolated target was rejected before `pg_restore`. The 100 GiB RTO rehearsal and independent recovery host remain `external_blocked`.

Replayed command result on 2026-09-28: `timescaledb_pre_restore` returned `t`, `timescaledb_post_restore` returned `t`, `schema_migrations` returned `6`, and the script printed `restore verified`. The copied sidecar validated after moving the dump and sidecar together to another directory; the guard exited non-zero before any restore when `IOLINK_RESTORE_TARGET` was absent.
